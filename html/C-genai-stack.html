Full circle: back to Block 0, the "model hosting" layer is just this: a very large function from tokens to a probability distribution over the next token, wrapped in sampling. Classically it descends from n-gram language models and softmax regression; the temperature knob is the Boltzmann temperature from statistical physics.

Recap questions (3)
  1. What is a token, and why does it matter to an architect more than "words" or "characters"? - A token is a sub-word chunk produced by the tokenizer; pricing, context limits and latency are all counted in tokens, and different languages, code and numbers tokenize at very different efficiency.
  2. What does temperature do, and when would you set it near zero for an enterprise use case? - It rescales the probabilities before sampling; low values make output more deterministic, which you want for extraction, classification and anything you need to regression-test. It does not remove hallucination.
  3. Why do models hallucinate, and what architectural levers reduce it? - They are trained to produce plausible continuations, not to retrieve verified facts; levers are grounding with retrieval (Block 3), tools that fetch facts (Block 4), structured outputs, and evaluation (Block 5).

Recap questions (3)
  1. Why use a schema (structured output) instead of asking the model to "reply in JSON"? - A schema lets the platform validate and, with provider support, constrain the output, so downstream code gets guaranteed shapes and you can retry or fail cleanly on violations.
  2. What goes in a system prompt versus the user message? - The system prompt holds stable role, rules, format and policy for every call; the user message holds the variable request and data. Treat the system prompt as configuration that is versioned and tested.
  3. In function calling, who actually runs the function? - Your application code does; the model only emits a structured request naming the tool and arguments, and your code executes it (with permission checks) and returns the result to the model.

Recap questions (3)
  1. Why does hybrid search (keyword plus vector) often beat vector-only retrieval? - Vector search is good at meaning and paraphrase but weak on exact identifiers, names and rare terms; keyword search is the reverse. Combining them, then reranking, covers both.
  2. A RAG answer is wrong. Name three places to look before blaming the model. - The chunking (answer split across chunks or lost), the retrieval (right document never returned, or wrong embedding/filters), and missing or stale source data; also permissions filtering out the document.
  3. Why must access control be applied at retrieval time in an enterprise knowledge base? - Because the model will happily summarise whatever it is given; if retrieval returns documents the user may not see, the model leaks them. Filter by the caller's entitlements before anything reaches the prompt.

Recap questions (3)
  1. When should you NOT use an agent? - When the steps are known and stable: a fixed workflow is cheaper, faster, easier to test and safer. Use agents only where the path genuinely cannot be specified in advance and the value justifies the cost and risk.
  2. What problem does MCP solve, and what does it not solve? - It standardises how an application connects models to tools and data (one protocol instead of N custom integrations). It does not solve authorisation, trust in third-party servers or tool quality; those remain your design work.
  3. Why does a long-running agent need durable execution? - Runs take minutes to hours, call flaky services and can crash; durable execution persists state so the run resumes without repeating side effects, which also gives you an audit trail.

Recap questions (3)
  1. Why start with error analysis rather than picking metrics up front? - Looking at real failures tells you which failure modes actually occur; generic metrics (helpfulness, tone) often miss the problems that matter, and your eval set should be built from observed failures.
  2. How do you trust an LLM-as-judge? - Calibrate it against human labels on a sample, keep the rubric narrow and binary, and re-check it when the judge model or prompt changes; otherwise you are measuring the judge.
  3. Which three things should a regression suite protect when you swap models or prompts? - Core task accuracy on a fixed gold set, known past failures (so they do not return), and safety/policy behaviours, with cost and latency tracked alongside.

Recap questions (3)
  1. What makes prompt injection different from SQL injection? - There is no reliable boundary between instructions and data inside a prompt, so you cannot sanitise it away; you limit damage by controlling what the agent can access and do (least privilege, no unmonitored exfiltration path) and by adding layered checks.
  2. What is the "lethal trifecta" and how do you break it? - Private data access, exposure to untrusted content, and an external communication channel in the same agent. Remove at least one leg (for example, no outbound network or no raw untrusted input).
  3. What does a bank need beyond guardrails to put an LLM system in production? - A governance trail: model inventory and risk tiering, documented purpose and limits, independent validation, ongoing monitoring, change control and human oversight, mapped to the applicable model-risk and compliance requirements.

Recap questions (3)
  1. When do you choose RAG, fine-tuning or prompting? - Prompting first for behaviour you can describe; RAG when the model lacks current or private facts; fine-tuning when you need consistent style, format or a cheaper smaller model on a narrow task, and you have good data.
