About this track and how to read it

The hands-on companion to Track D. Track D (bike) gives you the concepts of the general enterprise technology stack that sits UNDER the GenAI stack in Track C, by listening. Track E covers the same layers at the desk: you sit with paper, an editor and a terminal, and you pause, draw, type and run things. It is for someone who already knows enterprise Java well, so Spring and Java examples are preferred where the quality is equal, and beginner Java content is left out. It is not AWS service-by-service (you cover AWS separately in the SAA-C03 companion and the system-design guide), so the tools here are cloud-neutral or open source: Docker, Kubernetes, Terraform, Postgres, Redis, Kafka, Elasticsearch, Spring and Resilience4j. Where a cloud or vendor is named, it is only an example.

How it pairs with Track D. Watch a Track D block on the bike, then do the matching Track E block at the desk, with its lab. The concept comes first, the hands go second, and the Architect's question at the end of each block is the same one Track D asked, now with something you built behind your answer.

Work in the 0.1 order. (1) Write five functional and five non-functional requirements and one thing you will NOT do. (2) Estimate with your own assumptions (for example 20 million customers, 2,000 reads per second at peak, 10 consent changes per customer per year): reads and writes per second, storage per year, and what that implies for a cache and for the database. (7) End with a half-page of trade-offs and the two decisions you are least sure about. Full circle: you can take a vague one-line request and, in an hour, produce requirements, an order-of-magnitude capacity estimate, an API sketch, a data model and a C4 context and container diagram, and say which two decisions carry the most risk. You can also read someone else's diagram and ask the owner and data questions of each box.

Architect's question: What are the numbers (requests per second, data size per year, latency target) behind this design, and which box on the diagram breaks first when they double?

Recap questions (3)
  1. Q: In what order do the walkthrough videos build a design, and why do requirements and estimates come first? A: Requirements, API and core entities, high-level design, then deep dives (the chapter order of 0.1); requirements and rough numbers decide which parts of the design are hard, so you spend the deep dives there.
  2. Q: Why is an estimate within an order of magnitude usually good enough? A: The estimate exists to choose between kinds of design (one database or sharded, cache or no cache), and those choices change by factors of ten, not by 20 percent (the order-of-magnitude point is from 0.2's description; the reasoning is general knowledge).
  3. Q: What problem does "diagrams as code" with one model and several views solve? A: Hand-drawn diagrams drift out of sync with the software; defining the architecture once and generating each view from it keeps them consistent (from the 0.5 description).

Recap questions (3)
  1. Q: What does EXPLAIN ANALYZE show that EXPLAIN alone does not, and what plan change tells you an index helped? A: EXPLAIN shows the planned steps and EXPLAIN ANALYZE also runs the query and reports actual times and row counts; a sequential scan replaced by an index scan with a lower actual time is the evidence (general knowledge; 1.2's description only says EXPLAIN shows how Postgres plans to run a statement).
  2. Q: What are the three steps of cache-aside, and what can go wrong? A: Read the cache, on a miss read the database, then store the result in the cache; data in the cache can be stale after a write, which a TTL or explicit invalidation limits (general knowledge; 1.3 is title-based).
  3. Q: What does a Kafka consumer group guarantee about partitions and ordering? A: Each partition is read by one consumer in the group at a time, so order is kept within a partition and not across partitions, and events with the same key go to the same partition (the group and partition ideas are in the 1.5 chapter list; the ordering statement is general knowledge).

Lab (3-4 hours; take the smallest version first): build two small Spring Boot services, orders and payments, with Kafka and Postgres running locally. (1) orders accepts a POST and, in ONE database transaction, writes the order and an outbox row; a relay (a polling job is fine; Debezium is the stretch) publishes the outbox rows to a Kafka topic. (2) payments consumes the topic and records the payment idempotently, for example with a unique key on the message id so a repeated message changes nothing. (3) Add retry with a short back-off and a dead-letter topic to the consumer, and publish one poison message to prove it lands in the dead-letter topic. (4) Put a Resilience4j circuit breaker, retry and fallback around a call from orders to a deliberately flaky stub endpoint, and watch the breaker state in the actuator endpoint. (5) Optional: expose one call over gRPC or put a rate limit on the gateway. You know it worked if (a) killing payments mid-run and restarting loses no order events, (b) publishing the same message twice produces one payment, (c) the poison message sits in the dead-letter topic, not in a retry loop, and (d) the breaker opens after enough failures and closes again after the stub recovers.

Architect's question: If this call or message is repeated, delayed or lost, which write happens twice, which write is missing, and what in the design makes the second case harmless?

Recap questions (3)
  1. Q: Why write the order and the outbox row in one database transaction? A: Updating the database and publishing a message are two operations that can fail independently; one transaction makes the event exist if and only if the order exists, and a separate relay publishes it, so the worst case is a delayed or duplicate event, never a lost one (general knowledge; 2.4 is title-based).
  2. Q: Why must the consumer be idempotent even when the broker is reliable? A: A relay or broker can deliver the same message more than once after a failure or restart, so processing the same message id twice must change nothing (general knowledge).
  3. Q: What are the states of a circuit breaker and what moves it between them? A: Closed (calls pass), open (calls fail fast after too many failures) and half-open (a few trial calls after a wait); success closes it, failure re-opens it (general knowledge; 2.6 is title-based).

Recap questions (3)
  1. Q: Why must permissions be enforced at retrieval and not only at the application door? A: Otherwise the model can be handed text the user may not see, and no later filter reliably removes it from the answer; the Devoxx abstract filters vector queries against a list of authorized object IDs (from the 7.2 page; the reasoning is general knowledge).
  2. Q: What jobs does an LLM gateway do that an ordinary API gateway does not? A: It holds model credentials, guards and rewrites prompts, checks content safety, enforces usage and token limits, fails over by context and records usage for cost and observability (the list is from the 7.4 page).
  3. Q: Why run evaluations in CI as well as on production traffic? A: A golden set in CI catches regressions before a change ships, while scoring a sample of live traffic catches what the golden set never imagined and supplies new cases for it (general knowledge; 7.6 is title-based).
