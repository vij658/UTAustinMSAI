# Track G: End-to-end GenAI

**What this track is.** One progressive path through the whole life of a GenAI system, in the order you would actually build and run one, so that no stage is a cold start: each block comes after the blocks it rests on, and each ends with a small build step in one running project. It does not replace Tracks A to F. Track A (math), B (AI and ML concepts), C (the GenAI stack), D (enterprise stack, bike), E (enterprise stack, desk) and F (UT course tracker) already hold about 540 verified video rows; this track re-orders the best of them into one spine and adds new videos only where the lifecycle has a real gap. A reused row appears here under a Track G id, and a video is watched once, wherever it appears (progress is tracked by video ID).

**Stage order (Blocks 0 to 12).** 0 The build map; 1 Language-model basics; 2 Pretraining; 3 Post-training and alignment; 4 Adaptation; 5 Inference and serving; 6 Grounding and RAG; 7 Agents and tools; 8 Multimodal and diffusion; 9 Evaluation; 10 Safety and governance; 11 LLMOps and platform; 12 Capstone designs. The order logic: Blocks 1 to 3 are how a model comes to exist (reading one, making one, shaping one into an assistant), in the order a model is made even though you will adapt and serve long before you pretrain anything. Blocks 4 to 6 are how you make it yours and run it: choose between prompting, retrieval and tuning (4), serve it (5) and connect it to your documents (6). Blocks 7 and 8 widen what it can do (tools, and images and video). Blocks 9 to 12 wrap the system in what makes it enterprise-grade: evaluation, safety and governance, operations, and finally the whole-stack design. Blocks 0 to 6 are in this part of the file; the remaining blocks follow.

**The thread project.** Every Build it adds a piece to one system: an enterprise knowledge assistant for a bank-like company, built a stage at a time with open tools on public or synthetic data only (no employer data, nothing from work). A tiny GPT trained from scratch (Blocks 1 and 2); shaped with instruction and preference data and then tuned with a LoRA adapter (3 and 4); served locally with an inference server (5); grounded on a public-document corpus with RAG (6); turned into an agent with tools and MCP (7); evaluated (9); guarded and governed (10); run behind a gateway with tracing and cost tracking (11); and drawn and defended as a whole-stack design (12). Block 8 has no build step: the project stays text. Each Build it is a 1 to 3 hour desk step that runs on a laptop or a free tier and says how to know it worked; it is not a video.

**Block layout and the "Needs" convention.** Each block opens with why it matters for the stack, then **Needs** (what to have watched before, named by block in other tracks, for example "A4 probability, B4 transformers, F2 Deep Learning prep"; a block says "nothing" when it is a starting point), then **Pairs with** (the UT course in Track F and the Track C, D and E blocks that cover the same ground from another side). Then come the main table (4 to 7 rows, ordered from Start to Deeper), an optional table (0 to 4 rows), the **Build it** step, **Full circle** (how the block ties back to what you already know), **Architect's question** and three recap questions.

## Block 0: The build map

**Why it matters for the stack:** every later block is one stage of one system, and an architect who cannot place a tool, a risk or a cost on that map cannot judge it. This block gives the lifecycle in the order you would build and run it, the habit of asking "build, buy or borrow?" at every layer, and the small system you will grow through the rest of the track. Track C's stack map is a cross-section of a running system (which layers exist and who owns them); the stages here are the timeline of building it. The map below is my own framing for this track, not taken from a video, and its build, buy or borrow column is my judgement.

|-------|-----------------|---------------------|-----------------------------------|

| 3 Post-training and alignment | how a base model becomes an assistant | write instruction and preference data, run a small supervised pass | the aligned model is borrowed; your data for behaviour that matters is built |

**Build it (2 to 3 hours, desk):** train a tiny GPT from scratch on a small public text, and learn what "it works" means for a language model.
1. Put 1 to 2 MB of plain text from your charter's public documents in `stage-1/data/raw.txt` and hold out the last 10% for validation.
2. Before any neural network, compute two baselines on the validation text: the uniform-guess loss, ln(vocabulary size), and the loss of a character-bigram model (count which character follows which).
3. Following row 1.6, write or adapt a character-level GPT: 4 layers, 4 heads, 128-dimensional embeddings, a context of 128 characters. Train it for 10 to 20 minutes on a laptop CPU or a free GPU notebook and log training and validation loss.
4. Sample 200 characters at temperature 0.3, 0.8 and 1.2, and with top-k 10, and save three samples of each in `samples.md`; note one thing the model gets right (structure, headings, vocabulary) and one thing it gets wrong.
5. Run one ablation: remove the positional embeddings or cut the context to 16. Write your prediction of the validation loss first, then run it.

You know it worked if validation loss ends clearly below your bigram baseline (the model is using more than the previous character), the samples are word-like and echo the headings and layout of your documents, and the ablation moves the loss in the direction you predicted (or you can say why it did not). Keep three samples that read fluently but state something false: they are your first hallucination examples, and Block 6 asks whether retrieval fixes them.

**Full circle:** you can follow a sentence through a GPT: text to token ids, ids to vectors, vectors mixed by attention, a score for every possible next token, one token picked by a decoding rule; and you can say which step gets more expensive as prompts get longer. Classically it descends from n-gram language models: your bigram baseline is the old model the transformer has to beat.

**Architect's question:** What are the context length, the tokenizer and the decoding settings behind this answer, and which of them changed since we last tested?

<details>
<summary>Recap questions (3)</summary>

1. Q: Why does a longer prompt cost more than its extra tokens suggest? A: Attention compares each token with the tokens before it, so for full attention the work grows roughly with the square of the length, and the stored keys and values grow with it; row 1.3 explains why long prompts are not free.
2. Q: What do temperature, top-k and top-p change, and what do they leave alone? A: Only how the next token is picked from the model's probabilities: temperature reshapes the distribution (low is more deterministic), top-k keeps the k most likely tokens, top-p keeps the smallest set whose probabilities add up to p (row 1.5). None changes the weights, and none removes hallucination.
3. Q: In the Build it, what does a validation loss below the bigram baseline tell you? A: The model uses more than one previous character: attention is finding useful longer-range context. ln(vocabulary size) is the loss of a uniform guess and the bigram loss is the loss of using exactly one character of context.
</details>

## Block 2: Pretraining

**Why it matters for the stack:** few companies pretrain, but pretraining explains what you rent: which languages and code a model is good at (the data), why numbers and rare words behave oddly (the tokenizer), why modern small models are trained on far more tokens than a compute budget alone would suggest (serving cost), and what a training run needs (thousands of GPUs, fast interconnect, parallelism). That is the vocabulary for model cards, vendor claims and any "should we train our own?" meeting.

**Needs:** Block 1 of this track; A6 optimization; B3 neural networks and deep learning; F2 Deep Learning prep.

<details>
<summary>Recap questions (3)</summary>

1. Q: Why can't you swap a model's tokenizer after training? A: The embedding table and the output layer are indexed by token id, so a different vocabulary changes the meaning of every row; you would have to retrain or adapt the model. Vocabulary size also trades shorter sequences (cheaper attention) against a larger embedding and output layer.
2. Q: What is the Chinchilla result, and why do many modern small models train on far more tokens than it suggests? A: For a fixed training-compute budget, model size and training tokens should grow together; the usual summary is about 20 tokens per parameter (that summary is my background knowledge; row 2.4 covers the paper). Smaller models are over-trained beyond that because training is paid once and serving is paid on every request, so a smaller model that is cheaper to serve can win overall (the point of row 2.O3's title).
3. Q: What does ZeRO save compared with plain data parallelism, and what does it cost? A: Plain data parallelism keeps a full copy of the parameters, gradients and optimizer state on every GPU; ZeRO splits (shards) these across the GPUs so each holds only a part. The price is more communication between GPUs (rows 2.5 and 2.O4).
</details>

<summary>Recap questions (3)</summary>

1. Q: What is the KV cache, and why does serving many users stress memory more than compute? A: It stores the keys and values of tokens already processed so each new token computes only its own. It grows with layers, KV heads, head size, context length and the number of simultaneous requests, so memory caps concurrency; grouped-query attention shrinks it (row 5.2).
2. Q: What problem does PagedAttention solve? A: Caches differ in length and grow as a reply is generated, so giving each one a contiguous block wastes memory through fragmentation; storing them in small fixed-size blocks, like pages in virtual memory, lets more requests fit (row 5.3; the explanation is background knowledge of the vLLM paper).
3. Q: Why does continuous (in-flight) batching raise throughput compared with fixed batches? A: Requests join and finish at every decoding step instead of waiting for the longest reply in a fixed batch, so the GPU is not left idle (row 5.1 lists in-flight batching; the comparison is the standard one).

<details>
<summary>Recap questions (3)</summary>

1. Q: What does an approximate nearest-neighbour index such as HNSW trade? A: Exact search compares the query with every vector; an HNSW index (a layered graph of neighbours) finds near neighbours far faster at the cost of memory and a chance of missing the true nearest few, so recall is tuned against speed (row 6.2's chapters run from exact search to HNSW and IVF).
2. Q: A RAG answer is wrong. Name five places to look before touching the model. A: Whether the right document is in the index and current; how it was chunked; whether retrieval (embedding match, keyword match, filters, reranking) returned it; whether permissions removed it; and whether the prompt left it enough room (rows 6.4 and 6.5).
3. Q: Where should access control be enforced in a RAG system, and why? A: At retrieval, filtering results by the caller's entitlements before anything enters the prompt, because the model will use whatever it is given (row 6.6).
</details>
